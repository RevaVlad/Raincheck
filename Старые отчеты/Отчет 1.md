# Отчёт по приложению Raincheck

## 1. Доменная область

**Raincheck** — клиент-серверное приложение для согласования времени встреч внутри постоянной группы. Пользователь создаёт группу и опрос, приглашает остальных участников по ссылке, после чего каждый отмечает свою доступность на временной сетке и подтверждает ответ. На основе подтверждённых ответов приложение может определить наиболее подходящие интервалы для встречи.

Группа является постоянной сущностью: участники сохраняются между несколькими опросами.

## 2. Стек реализации

- **Frontend:** Angular 22, TypeScript, Angular Material, Tailwind CSS.
- **Backend:** Node.js, TypeScript, Fastify, Prisma 7, PostgreSQL.
- **Инфраструктура и разработка:** Git, npm, Docker Compose, Nginx для раздачи frontend и проксирования API, GitHub Actions, конфигурация через переменные окружения.

Frontend и backend находятся в одном репозитории и образуют единое клиент-серверное приложение.

## 3. Основные сущности доменной области

- **Group** — постоянная группа участников с названием и кодом приглашения.
- **Participant** — участник группы с отображаемым именем.
- **Poll** — опрос по времени встречи: содержит диапазон дат, дневной диапазон времени, часовой пояс, шаг сетки, длительность встречи и состояние `OPEN` или `CLOSED`. Опрос может ссылаться на предыдущий опрос группы для подсказок доступности.
- **PollResponse** — ответ участника на опрос. Может находиться в состоянии `DRAFT` или `CONFIRMED`.
- **AvailabilityInterval** — интервал доступности участника. Поддерживаются типы `UNAVAILABLE`, `IF_NEEDED` и `PREFERRED`; для предпочтительного интервала хранится направление предпочтения.

## 4. Соответствие методологии 12 факторов

### 1. Codebase

Raincheck хранится в одном Git-репозитории, в котором находятся frontend, backend и конфигурационные файлы проекта. Один и тот же исходный код предполагается использовать в разных окружениях, а различия между ними задаются конфигурацией.

### 2. Dependencies

Зависимости явно описаны в отдельных `package.json` для корня проекта, frontend и backend и зафиксированы соответствующими lock-файлами. В CI для всех трёх наборов зависимостей используется `npm ci`; глобально установленные Node.js-пакеты не требуются.

### 3. Config

Конфигурация backend передаётся через переменные окружения. Используются `NODE_ENV`, `HOST`, `PORT`, `DATABASE_URL` и `LOG_LEVEL`. Файл `backend/.env` исключён из Git, а `backend/.env.example` содержит только пример локальной конфигурации без реальных секретов.

### 4. Backing services

PostgreSQL используется как внешний подключаемый ресурс. Backend получает строку подключения через `DATABASE_URL`, поэтому локальный или внешний экземпляр PostgreSQL можно заменить без изменения исходного кода приложения.

### 5. Build, release, run

Сборка и запуск разделены: backend компилируется из TypeScript в JavaScript, frontend собирается в статические файлы. В Docker Compose frontend раздаёт Nginx, а миграции выполняет отдельный сервис `migrate` до запуска API. В репозитории нет процесса выпуска версионированных неизменяемых релизов и автоматического отката.

### 6. Processes

Fastify backend не хранит постоянное состояние приложения в памяти процесса. Данные групп, участников, опросов, ответов и интервалов доступности сохраняются в PostgreSQL, поэтому перезапуск backend не приводит к потере пользовательского состояния.

### 7. Port binding

Fastify является самостоятельным HTTP-сервером и напрямую слушает сетевой порт. Значения `HOST` и `PORT` задаются через конфигурацию окружения, поэтому для работы backend не требуется внешний application server.

### 8. Concurrency

Backend не хранит пользовательское состояние в памяти, поэтому его архитектура допускает несколько экземпляров Fastify с общей PostgreSQL. Конфигурация Docker Compose описывает один экземпляр API; горизонтальное масштабирование в ней не настроено. Отдельные `worker` и `cron` процессы в проекте не используются.

### 9. Disposability

Backend обрабатывает `SIGTERM` и `SIGINT`, корректно закрывает Fastify и соединение Prisma. Состояние приложения хранится в PostgreSQL, поэтому остановка и повторный запуск web-процесса не приводят к потере данных.

### 10. Dev/prod parity

Локальная разработка и CI используют PostgreSQL и один и тот же стек приложения. В CI также выполняются миграции, проверки и сборка. В репозитории есть Docker Compose стек с PostgreSQL, миграциями, API и frontend; сведений о фактическом production-развёртывании и его соответствии локальной среде в репозитории нет.

### 11. Logs

Backend использует логгер Fastify и выводит логи в `stdout`/`stderr`. Приложение не управляет локальными файлами логов и не зависит от конкретной системы их централизованного сбора.

### 12. Admin processes

Миграции Prisma запускаются отдельной командой, а не внутри Fastify при старте приложения. В CI они выполняются отдельным шагом, а в Docker Compose — сервисом `migrate` до запуска API. Часть ограничений PostgreSQL задана непосредственно в проверенных SQL-миграциях и не полностью выражается схемой Prisma; изменение схемы требует проверки этих ограничений. Для этой схемы нельзя использовать `prisma db push` или `prisma migrate dev` вместо проверенных SQL-миграций.

## 5. Итог

Raincheck реализует основные требования 12-factor на уровне архитектуры приложения: зависимости и конфигурация явно заданы, PostgreSQL используется как внешний сервис, backend не хранит состояние процесса, самостоятельно экспортирует HTTP API через порт, корректно завершает работу, пишет логи в `stdout` и запускает миграции отдельно.

Для приложения подготовлен Docker Compose стек, но в репозитории нет подтверждения фактического production-развёртывания, процесса выпуска версионированных неизменяемых релизов и автоматического отката. Поэтому соответствие требованиям, зависящим от реальной эксплуатации, нельзя проверить полностью.
